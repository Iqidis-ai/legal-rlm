**Findings**
- Medium: `reload_pending_from_db()` is not logically thread-safe against concurrent `flush_revisions()` calls. It does an unlocked DB scan at [`src/irys/matter/matter.py`](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L127) and only takes queue locks while reinserting rows at [`src/irys/matter/matter.py`](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L146) and [`src/irys/matter/matter.py`](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L154). `flush_revisions()` calls reload immediately before draining at [`src/irys/matter/runtime.py`](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/runtime.py#L463) and [`src/irys/matter/runtime.py`](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/runtime.py#L466). If flush A has already drained a durable row and is replaying it while its DB row still exists, flush B can reload that row from DB, reinsert it into memory, and drain/process it again. The service shares live `MatterModel` instances across requests via [`src/irys/service/api.py`](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/service/api.py#L55) and exposes standalone flushes at [`src/irys/service/api.py`](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/service/api.py#L1514), so this race is reachable.

**Assessment**
The original HIGH is fixed for the non-concurrent case: if `delete_pending_propagation_db()` silently fails, the next flush on the same live model will reload and see those rows again. But `reload_pending_from_db()` is only dict-safe, not flush-safe, so I would not mark the patch CLEAN.

Calling reload at flush start does introduce double-replay risk for durable correction/evidence rows another flush is currently processing. It does not create a new issue for the adapter-local `_pending_assertion_ids`; the risk is the durable queue’s drain-to-delete window.

The batched `db.transaction()` in `enqueue_*_pending()` at [`src/irys/matter/matter.py`](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L333) and [`src/irys/matter/matter.py`](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L408) does change semantics: per-row best-effort persistence becomes all-or-nothing batch persistence on error. I do not see that as a separate correctness bug by itself, but restart survivability after a mid-batch DB error is weaker than before.
