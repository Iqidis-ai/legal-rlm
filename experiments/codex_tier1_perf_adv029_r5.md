**Findings**
1. Medium: the enqueue path is still doing one durable write per assertion, with no batching. Both pending-queue writers loop `ids` and call `INSERT OR REPLACE` row-by-row ([matter.py:278](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L278), [matter.py:343](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L343)). In this codebase `db.execute(...)` runs in autocommit mode unless wrapped, so a large truncation frontier still becomes hundreds or thousands of separate WAL commits. `r5` fixed the drain-side batching, but the write side is still not performance-clean at scale. This should be one transaction or `executemany()` per enqueue batch.

2. Low: the new flush-time `proof_state` refresh is reasonably shaped, but each affected issue still pays an avoidable read-before-write probe. `flush_revisions()` batches the assertion→issue lookup, preloads overrides once, and wraps recompute writes in one transaction ([runtime.py:440](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/runtime.py#L440), [runtime.py:570](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/runtime.py#L570), [runtime.py:597](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/runtime.py#L597)), but `compute_and_store()` still does `SELECT id FROM proof_state ...` before deciding between `UPDATE` and `INSERT` ([graph.py:3523](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/graph.py#L3523)), even though there is already a unique `(matter_id, issue_id)` index to support an upsert ([schema.py:631](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/schema.py#L631)). Not a blocker, but still measurable on large affected-issue sets.

**Assessment**
No, I would not call `adv#029` fully CLEAN from a performance perspective yet. The major scale hazards that motivated the review are fixed: drain-side select is chunked, delete is by PK in 900-item batches, and flush-side proof recompute is targeted rather than `compute_all()`. What remains is one real medium-cost hotspot on the enqueue side, plus one smaller per-issue inefficiency in proof-state persistence.
