**Assessment**
- `_apply_with_truncation()` always doing `list(pending)` is not a meaningful regression. On the no-truncation path, `pending` is empty by definition, so this is just one empty-list allocation after an `apply()` that already paid for the override query and per-node DB work. Ref: [belief_revision.py:373](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/belief_revision.py#L373)
- `apply()` doing `_collect_unvisited.extend(unvisited)` is also low-risk. It only runs on truncation, the current caller passes a fresh empty list each round, and the copied frontier is capped by the remaining queue, not the whole graph. Compared with `_revise_one()` plus `get_dependents()`, this copy is noise. Refs: [belief_revision.py:433](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/belief_revision.py#L433), [matter.py:278](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L278)

Each visited seed pays at least `get()`, `get_neighbor_belief_states()`, and `get_dependents()`; changed nodes pay more write-side queries. So end-to-end HTTP latency is still a seconds-scale tail-risk under large corrections.
