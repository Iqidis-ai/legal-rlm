**1. Store Design**
Conventions: one SQLite DB per repository at `repository/.irys/matter.sqlite3`; `TEXT` ULID PKs, ISO-8601 UTC timestamps, `INTEGER` booleans, `REAL` scores, `matter_id` FK everywhere, `STRICT` tables, FTS5 on text lookup tables, and junction tables for multi-span / multi-issue / multi-actor relations.

- `MatterRegistry`: tables `matter`, `matter_party`, `matter_deadline`, `matter_objective`; fields: identity, repo root, forum, posture, governing law, maturity, parties, deadlines, objectives; queries: open matter by repo path, list deadlines/objectives/parties, maturity snapshot; indexes: unique `(repository_root)`, `(matter_name)`, `(matter_id, side)`, `(matter_id, due_at, status)`, `(matter_id, priority, status)`.
- `RepositoryInventoryStore`: `document_inventory`, `document_relation`, `document_processing`; fields: stable doc id, relative path, storage URI, SHA-256, size, modified/discovered times, ingest/parse status, duplicate cluster, family id, version chain id, salience, read stats; queries: lookup by path/hash, unread high-salience docs, duplicates, version chains, likely missing companions; indexes: unique `(matter_id, relative_path)`, unique `(matter_id, sha256)`, `(ingest_status, parse_status)`, `(family_id)`, `(version_chain_id)`, `(salience_score DESC, last_read_at)`, relation `(source_doc_id, relation_type)` and `(target_doc_id, relation_type)`.
- `DocumentCardStore`: `document_card`, `document_actor_role`, `document_issue_salience`; fields: title, filename, type/subtype, source side, creation/sent/effective/discovery dates, purpose, rhetorical posture, reliability posture, privilege/confidentiality, operative status, unresolved metadata; queries: operative docs by type/date, docs by actor/side, docs relevant to issue, metadata gaps; indexes: `(doc_type, subtype)`, `(source_side, operative_status, effective_date)`, actor-role `(actor_id, role)`, issue `(issue_id, salience_score DESC)`, partial index on unresolved flags.
- `SpanStore`: `span`; fields: `document_id`, `span_type`, page/line/char locators, section/clause/table/cell locators, `parent_span_id`, `ordinal_in_doc`, `text_hash`, `span_text`, `parser_version`; queries: exact provenance for assertions/evidence/quants, fetch clause/table cell, resolve citations; indexes: `(document_id, span_type, ordinal_in_doc)`, `(document_id, page_start, line_start)`, `(parent_span_id)`, unique `(document_id, text_hash, span_type, page_start, char_start)`.
- `ActorStore`: `actor`, `actor_alias`, `actor_contact`, `actor_affiliation`, `actor_relationship`; fields: canonical name, normalized name, actor type, home side, role/title history, alias/email/domain, firm-party relationships, agenda/reliability notes; queries: alias/email resolution, who speaks for whom, counsel-party map, role changes over time; indexes: unique `(matter_id, normalized_name)`, unique alias/contact values, affiliation `(org_actor_id, start_date, end_date)`, relationship `(actor_id, relation_type)` and `(related_actor_id, relation_type)`, FTS5 on alias text.
- `AssertionStore`: `assertion`, `assertion_occurrence`, `assertion_link`, `assertion_issue_link`, `belief_revision_event`; `assertion` holds canonical typed proposition with `model_layer`, `assertion_kind`, subject/predicate/object refs or JSON, temporal scope, current belief state, confidence; `assertion_occurrence` holds `document_id`, `span_id`, `speaker_actor_id`, `source_role`, `source_side`, `speech_act`, `origin_kind`; queries: upsert canonical proposition, fetch all occurrences, graph traversal, supersession/conflict, issue-linked assertions; indexes: unique `(matter_id, proposition_key)`, `(subject_ref_type, subject_ref_id, predicate_key)`, occurrence `(assertion_id, speech_act)` and `(document_id, span_id)`, link `(src_assertion_id, link_type)` and `(dst_assertion_id, link_type)`, issue link `(issue_id, relation_type)`, revision `(root_assertion_id, created_at)`. Critical rule: speech act is occurrence-level; belief state is canonical-assertion-level.
- `EvidenceStore`: `evidence_link`; fields: `target_type`, `target_id`, `source_type`, `source_id`, `relation_type` (`support`, `attack`, `corroborate`, `authenticate`, `contradict`), proof weight, source diversity, authentication/admissibility status, vulnerability JSON, note; queries: strongest support/attack for issue/assertion, corroboration across independent sources, proof vulnerabilities; indexes: `(target_type, target_id, relation_type, proof_weight DESC)`, `(source_type, source_id)`, partial indexes for unresolved authentication/admissibility problems.
- `IssueStore`: `issue`, `issue_predicate`, `issue_theory`, cached `issue_coverage`; fields: tree structure, issue type, burden side, materiality, salience, predicates, theories, status; queries: issue tree traversal, per-element coverage, weakest-covered predicates, theory comparison, support/attack/gap counts; indexes: `(parent_issue_id, sort_order)`, `(issue_type, status)`, predicate `(issue_id, status)`, coverage `(issue_id, coverage_score)` and `(predicate_id)`.
- `AssumptionStore`: `assumption`, `assumption_link`, `assumption_support`; fields: statement, rationale, invalidation condition, source kind (`system`/`user`), status (`temporary`/`provisional`/`accepted`/`rejected`), downstream targets; queries: active assumptions carrying an issue, user-supplied assumptions, invalidation blast radius; indexes: `(status, source_kind)`, link `(target_type, target_id)`, support `(assumption_id, source_type, source_id)`.
- `GapStore`: `gap`, `gap_link`; fields: gap type, description, expected artifact, materiality, blocker score, status, resolution note, affected objects; queries: open gaps by materiality, missing documents, gaps blocking issue coverage, unresolved contradictions; indexes: `(gap_type, status, materiality_score DESC)`, link `(affected_type, affected_id)`.
- `QuantStore`: `quant_fact`, `quant_relation`; fields: kind, decimal/date/range/rate/currency/unit values, raw text, subject object, source span, linked assertion, reconciliation/formula links; queries: invoice-payment reconciliation, damages components, numeric conflicts, date overlap checks; indexes: `(quant_kind, date_value)`, `(currency, amount_value)`, `(subject_type, subject_id)`, `(assertion_id)`, relation `(from_quant_id, relation_type)` and `(to_quant_id, relation_type)`.
- `AuthorityStore`: `authority`, `authority_issue_link`; fields: normalized citation, jurisdiction, court/source type, date, holding/rule, scope, treatment, posture, freshness, issue role (`supportive`/`adverse`/`limiting`); queries: governing authorities by issue/jurisdiction/posture, adverse authority surfacing, freshness; indexes: unique normalized citation, `(jurisdiction, source_type, decision_date DESC)`, issue link `(issue_id, relation_type, strength DESC)`.
- `ReasoningLedger`: `run_session`, `ledger_event`; `run_session` holds query, objective, active branch issue, status, stop/redirect flags, next action; `ledger_event` is ordered append-only user-facing state transitions with `event_type`, `why`, `summary`, changed object refs, branch, snapshots; queries: current objective/branch/next action, recent model changes, full run replay, user interrupt/redirect; indexes: `(matter_id, status, started_at DESC)`, `(run_id, seq_no)`, `(branch_issue_id, seq_no)`, `(event_type, created_at)`, `(changed_object_type, changed_object_id)`.

**2. Storage Technology**
- Decide definitively for SQLite, not “SQLite maybe”: one per-matter DB, WAL mode, `foreign_keys=ON`, `STRICT` tables, JSON1, FTS5, recursive CTEs.
- SQLite fits the actual query mix: document/actor/issue lookups are relational joins; issue coverage is aggregate-heavy; ledger is append-only; assertion traversal is adjacency-list recursion. Those are all strong SQLite workloads.
- Belief revision should use SQLite as source of truth plus a per-run in-memory adjacency cache loaded from `assertion_link`; that gives fast hot-path propagation without introducing Neo4j.
- Reject JSON files because no ACID/indexes; DuckDB because this is OLTP plus incremental graph updates, not analytic batch SQL; Neo4j because graph traversal is only one slice of a mostly relational substrate; PostgreSQL is the migration path only if multi-user writes or fuzzy alias matching outgrow SQLite.
- Revisit only if A-007 fails in practice: >100k assertions with revision latency consistently above 1s or concurrent writers become a real requirement. Until then, D-004 should move from proposed to active.

**5. Migration**
- Persist immediately: issues, actors/entities, citations as spans/occurrences, contradictions as evidence attacks or gaps, evidence strength inputs, timeline dates as quant/assertion data, hypotheses as theories/assumptions plus ledger events, query classification and plan as run metadata.
- Keep ephemeral: lead queue, recursion depth, pending tasks, iteration counts, token estimates, progress percent, checkpoint bookkeeping, raw prompt text.
- Do not delete public state surfaces in phase 1; delete state ownership instead. `state.py` should stop being the system of record for facts/entities/evidence/contradictions/timeline/feedback and become a run-local projection/scratchpad.
- First deprecations in `state.py`: `add_fact`, `add_entity`, `add_evidence`, `add_contradiction`, `add_cross_reference`, `add_timeline_event`, `recalculate_evidence_strength`, feedback-driven lead mutation. Those should delegate into `MatterRuntimeAdapter` once attached.
