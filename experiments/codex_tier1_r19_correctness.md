**Findings**
- High: OCC retry exhaustion can now be misreported as full convergence. `_apply_with_truncation()` sets `truncated` when `occ_exhausted_count > 0`, but only returns `list(pending)` as `unvisited` ([belief_revision.py#L375](/C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/belief_revision.py#L375), [belief_revision.py#L376](/C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/belief_revision.py#L376)). If the only failure mode is an exhausted OCC-aborted node, `unvisited` is empty. `correct_assertion()` then overwrites `result.propagation_truncated = bool(_pending)` ([matter.py#L273](/C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L273), [matter.py#L295](/C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L295)), clearing the warning even though a node/subtree was abandoned and may be stale.
- High: `RevisionResult.truncation_pending` never reaches clients. The field exists on the dataclass ([models.py#L97](/C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/models.py#L97)), but the REST response drops it ([api.py#L1774](/C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/service/api.py#L1774)) and the in-process backend reduces it to a generic warning ([in_process.py#L231](/C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/ui/backends/in_process.py#L231)). With the new 3-round cap, remote callers have no actionable frontier to resume.
- Medium: v39 is still not atomic. The DB wrapper opens SQLite with `isolation_level=None` ([db.py#L54](/C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/db.py#L54)), and the repo already notes that explicit `BEGIN` is required in that mode ([schema.py#L909](/C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/schema.py#L909)). `with conn:` in v39 ([schema.py#L1506](/C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/schema.py#L1506)) does not actually close the DROP/CREATE window.

**Answers**
1. Shared-state removal is good. For pure `MAX_WORK` truncation, `list(pending)` is the right frontier and preserves queue order. Edge case: it does not include OCC-abandoned nodes/subtrees, so `unvisited` is incomplete when truncation is caused by retry exhaustion.
2. `_collect_unvisited` is only extended when `truncated` is true, and it is request-local, so concurrent callers no longer bleed into each other. It still inherits the OCC-exhaustion gap above.
3. `force_state().truncation_pending` is set correctly from `_apply_with_truncation()` and survives the write transaction as an in-memory return value. It does not survive the API boundary because serializers omit it.
4. The retry loop is correct for request-local frontier handling. Resetting `propagation_truncated` to `False` is correct only when truncation was frontier-based and fully drained; it is wrong for OCC-retry exhaustion. The 3-round cap is only a sound tradeoff if leftover work is durably queued or fully exposed to clients; right now it is neither.
5. `RevisionResult.truncation_pending` is not serialized anywhere I found. The manual REST response omits it, and there is no response model/test covering it.
6. The v39 `with conn:` wrapper is not the right SQLite transaction boundary under this connection setup. Use explicit `BEGIN`/`COMMIT` or the project transaction helper.
7. New correctness issues introduced: the false-negative `propagation_truncated` reset, the lost `truncation_pending` at serialization boundaries, and the ineffective v39 transaction wrapper.

I did not run the test suite; this was a static review.
