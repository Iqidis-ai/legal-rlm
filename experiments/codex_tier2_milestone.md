**Direct Answers**
1. Truth maintenance: no, not in the JTMS/non-monotonic-reasoning sense. Yes, it can retract a belief when its only `supports` assertion becomes `disputed/withdrawn/superseded/unknown`; that path falls to `unknown` and propagates downstream. But that is a narrow case, not a correct general implementation. `depends_on` is currently semantically broken: it propagates but does not count as support. I would either make `depends_on` part of support computation or delete it until implemented.

2. Layer separation: no. The five layers have effectively collapsed into one canonical `assertion` store with a label. Worse, the unique key actively merges same-text propositions across layers. Proof/evidence is not operationally separate yet; `evidence_link` exists in schema, but the active graph/revision path does not use it. If SO-2/SO-4 matter, this needs to change before more data lands.

3. Scaling ceiling:
- Truly O(n) or scan-heavy today:

Practical ceiling: 100K assertions is not itself the problem; SQLite can handle that. The current design likely stays workable around 100K assertions if revisions are local. It starts degrading when one run touches thousands of assertions or when link rows get into the few-hundred-thousand range, because the revision engine becomes query-chatty. I would treat low-hundreds-of-thousands of assertions plus a few-hundred-thousand links as the current interactive ceiling before multi-second latencies become normal.

4. Pre-SO-6/SO-7: structural changes are needed now.
- Replace assertion identity. Minimum fix: unique/index and lookup on `(matter_id, model_layer, proposition_key)`. Better fix: add a `proposition` table and make layer-specific assertions separate rows pointing to it.
- Add a real migration system before touching this, because the current runner cannot safely change assertion identity.
- Add `ix_link_src_type(src_assertion_id, link_type, dst_assertion_id)`.
- Add matter-aware gap indexes and a stable gap dedup key; right now the same missing document can be inserted repeatedly.
- Add normalized issue title storage plus unique/index on `(matter_id, parent_issue_id, issue_type, normalized_title)`.
- For SO-6, add indexes on `quant_fact(assertion_id)` and `quant_fact(span_id)`, and make `span_id` an actual FK before you depend on numeric provenance.

5. Highest risk: the decision to make canonical assertion identity equal to normalized proposition text within a matter. That single choice is what collapses layers, makes later proof/legal/decision-context modeling awkward, and turns the eventual migration into a table-rebuild plus relinking exercise across `assertion_occurrence`, `assertion_link`, `belief_revision_event`, `assertion_issue_link`, and future quant/gap references.
