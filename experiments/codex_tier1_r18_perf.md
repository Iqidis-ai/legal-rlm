**Findings**
- High: `_truncation_pending` is stored on the shared `BeliefRevisionEngine` instance, not on a request-local object ([belief_revision.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/belief_revision.py#L240)). The service caches one `MatterModel` per `matter_id` in `_active_matter_models` ([api.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/service/api.py#L55)), populates that cache on wiring ([api.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/service/api.py#L192)), and returns the same instance for later requests ([api.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/service/api.py#L256)). If one correction hits the 10-round cap in `[matter.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L263)`, leftover pending IDs remain on the engine and the next correction can drain unrelated work. With real concurrency, the set is also unsynchronized. This is both a correctness leak and a latency amplifier across requests.
- High: the retry loop now puts worst-case wide-propagation cleanup directly on the HTTP critical path. `force_state()` already runs one truncated BFS over dependents ([belief_revision.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/belief_revision.py#L776)), and `MatterModel.correct_assertion()` can add 10 more `apply()` passes ([matter.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L263)). Each pass can spend up to 2000 visits when the seed frontier is large ([belief_revision.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/belief_revision.py#L295)), so the static upper bound is 22,000 `_revise_one()` visits before the response returns, plus the follow-on proof-state recompute ([matter.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L291)). On a simple 5000-assertion fan-out this is closer to 3 passes and about 5000 visits, but convergent graphs can still consume the full 22k-visit budget because visits, not unique nodes, are capped. Since the REST handler waits synchronously inside the async endpoint ([api.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/service/api.py#L1712)), yes, this can block the HTTP response too long for an interactive correction path.
- Medium: v39 rebuilds `ix_assertion_revision_lock` with `DROP INDEX` followed by `CREATE INDEX` ([schema.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/schema.py#L1490)), and `apply_schema()` does not wrap a migration in one explicit transaction ([schema.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/schema.py#L1557)). On the first open of an old DB after deploy, SQLite will do a full index rebuild inline, writers will wait while `CREATE INDEX` scans `assertion_revision`, and there is a brief autocommit window after `DROP` where the old index is already gone. That is a real locking/stall risk on an active DB.

**Notes**
- The new `for r in results: r.propagation_truncated = True` loop is O(results) ([belief_revision.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/belief_revision.py#L444)), but it is just in-memory attribute assignment over already-built objects. Relative to the per-node SQLite work in `_revise_one()`, it is not a meaningful regression.
- Other introduced costs are secondary: each retry re-runs the trust-override preload query in `_apply_with_truncation()` ([belief_revision.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/belief_revision.py#L252)), and the larger `propagated_to` set now widens the issue lookup and `proof_state.compute_and_store()` fan-out in the same request ([matter.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L291)). Those compound the latency increase, but the two main issues above dominate.
