**Findings**
- High: `_focus_issue_id` is not reliably the semantically correct issue for a search lead, but the new resolver trusts it completely. Initial searches are assigned by position, not by explicit issue mapping ([engine.py:1285](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L1285), [engine.py:1289](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L1289)), and duplicate leads keep the first non-`None` focus id even if a later duplicate belongs to a different issue ([state.py:784](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/state.py#L784), [state.py:789](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/state.py#L789)). - High: `predicates_satisfied` is never checked against the exact elements shown to the model. The prompt only injects the first two open predicates for the issue ([engine.py:3181](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L3181)), but orientation can store up to four and create predicate leads beyond those two ([engine.py:1271](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L1271), [engine.py:1334](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L1334)). The resolver then accepts any exact-match description on that issue ([engine.py:2014](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L2014), [graph.py:1551](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/graph.py#L1551)). So the model can resolve a same-issue predicate that was not actually in the `Issue Focus` block. The `[:8]` cap ([engine.py:2011](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L2011)) does not guard this; it is looser than the prompt-visible max.

- Medium: Description matching is too brittle for the prompt format. `Issue Focus` renders each element in quotes ([engine.py:3186](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L3186)) and the prompt asks for the “exact text” ([engine.py:254](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L254)), but the code only does `_ps.strip()` before exact SQL equality ([engine.py:2015](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L2015), [graph.py:1551](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/graph.py#L1551)). If the LLM returns `"predicate text"` including the quotes, or minor casing/punctuation drift, resolution silently fails.

- Medium: The cache key does not cover the actual Issue Focus contents. `_analysis_key` only includes `_focus_issue_id` ([engine.py:1802](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L1802)), but the prompt depends on the current open predicates for that issue ([engine.py:1819](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L1819), [engine.py:3181](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L3181)). Once one predicate resolves and the top-two open predicates change, warm-cache hits can replay stale `predicates_satisfied`.

- Medium: Predicate resolution is not gated on persisted evidence. Fact persistence only runs when `key_facts` is truthy ([engine.py:1848](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L1848)), but `predicates_satisfied` is processed unconditionally afterward ([engine.py:2009](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L2009)). A malformed or cached response could mark a predicate resolved even when no supporting fact was recorded from that analysis pass.

**Assessment**
The direct API call is mechanically correct: it does call `resolve_predicate_by_description()` with `_focus_issue_id` and the returned description ([engine.py:2014](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/rlm/engine.py#L2014)). The correctness problems are upstream: focus attribution is heuristic, the returned descriptions are not allowlisted to the prompt-visible elements, and the description normalization is too weak.

On hallucinations: strings not present on that issue are mostly safe no-ops because the update requires the same `issue_id` and exact `description` ([graph.py:1551](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/graph.py#L1551)). The unsafe case is a hallucinated or inferred string that matches another open predicate on the same issue, especially one not shown in the prompt.

The cap of 8 is not appropriate as a correctness guard. The prompt currently exposes at most 2 elements, so the safe bound should be the exact allowlisted set size, not `8`.
