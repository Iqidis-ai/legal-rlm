**Findings**

No perf finding on `147f16d` itself.

Forcing fan-out after a successful OCC retry does not look like meaningful BFS expansion overhead. That path is only taken for nodes that already hit an OCC abort and were re-enqueued, it is capped per node at 3 retries, and the added work is just one extra downstream sweep for that conflicted node’s dependents ([belief_revision.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/belief_revision.py#L288), [belief_revision.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/belief_revision.py#L349)). Dependent lookup is a single indexed query, not an N+1 walk ([graph.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/graph.py#L374), [schema.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/schema.py#L696)). So in normal operation this is bounded corrective work, not a meaningful new frontier explosion. The only case where it becomes noticeable is already-pathological write contention, where it may eat `MAX_WORK` faster, but contention is the real bottleneck.

Other perf concern nearby, but pre-existing rather than introduced here: the engine fans out on any non-null revision result ([belief_revision.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/belief_revision.py#L349)), including confidence-only updates ([belief_revision.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/belief_revision.py#L643), [belief_revision.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/belief_revision.py#L650)), while downstream recompute only consumes neighbor states/source roles, not neighbor confidence ([graph.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/graph.py#L439), [graph.py](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/graph.py#L558)). If you want the next perf cleanup, that is the one to tighten.
