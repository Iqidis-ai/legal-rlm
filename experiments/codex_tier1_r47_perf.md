**Findings**
1. `LOW` — Holding the queue lock across the DB transaction is a real contention vector if SQLite is slow or waiting on another writer, because the caller can sit inside the lock while `busy_timeout=5000` is in effect. See [matter.py#L337](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L337), [matter.py#L407](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L407), [db.py#L62](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/db.py#L62), [db.py#L93](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/db.py#L93).  
Compared to the immediately prior pattern, this is not a new regression: the lock already wrapped the same batch transaction. `758038d` only moved the dict write from before commit to after commit, so lock hold time is effectively unchanged. If you mean pre-batching history, current code is still better than the old per-ID write pattern.

2. `CLEAN` — The `enqueue_evidence_pending()` move in `set_trust_override()` is perf-neutral. See [matter.py#L653](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L653), [matter.py#L686](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L686).  
It adds one always-created list and one unconditional call that fast-returns on empty input. The dominant cost on this path is still `apply_revision()` and proof-state recompute, not the moved enqueue.

3. `LOW` — Other perf concern nearby: `set_trust_override()` still recomputes proof state one issue at a time without an outer transaction, unlike the already-optimized correction/flush paths. See [matter.py#L692](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L692), [matter.py#L709](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L709), versus [matter.py#L604](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L604) and [runtime.py#L607](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/runtime.py#L607).  
On a wide fan-out trust override, that N-commit pattern will matter more than `de95dd1`.

4. `LOW` — Separate residual cost from recent queue work: every flush still scans `pending_propagation` for the whole matter before draining. See [matter.py#L138](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/matter.py#L138), [runtime.py#L472](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/runtime.py#L472), [schema.py#L1547](C:/Users/devan/OneDrive/Desktop/Projects/legal-rlm/src/irys/matter/schema.py#L1547).  
Probably fine while the table stays small, but it is linear in backlog size.

No `HIGH` or `MEDIUM` perf regressions found in `758038d` / `de95dd1`. The new enqueue ordering is basically perf-neutral; the main remaining costs are pre-existing DB serialization and unbatched trust-override proof-state writes.
