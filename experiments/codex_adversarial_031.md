**Findings**
1. High: SO-2 is still only partially audited. The new history endpoint closes the read-path gap, but not the completeness gap. `GET /matter/{matter_id}/assertions/{assertion_id}/history` only exposes rows that already exist in `assertion_revision` [`src/irys/service/api.py:1666`](../src/irys/service/api.py#L1666), [`src/irys/matter/graph.py:283`](../src/irys/matter/graph.py#L283). The canonical NULL -> non-NULL SPO enrichment path still mutates `subject_ref_type`, `subject_ref_id`, `predicate_key`, `object_json`, and temporal scope directly with no `write_revision_rows()` call at all [`src/irys/matter/graph.py:203`](../src/irys/matter/graph.py#L203). I reproduced this locally: after a same-proposition richer second occurrence upgraded the canonical SPO payload, `assertion_revision` remained empty while the assertion row changed. Pre-v34 mutations are also permanently absent by design [`src/irys/matter/schema.py:1395`](../src/irys/matter/schema.py#L1395). Verdict: the endpoint fixes visibility of recorded revisions, not completeness of revision recording.

2. High: SO-3 stop/redirect is still not concurrency-safe enough to call "reliable". The API validates run state first, then calls ledger primitives that blindly update by `id` without requiring `status='running'` and without checking affected row count [`src/irys/service/api.py:1399`](../src/irys/service/api.py#L1399), [`src/irys/service/api.py:2563`](../src/irys/service/api.py#L2563), [`src/irys/matter/reasoning.py:208`](../src/irys/matter/reasoning.py#L208), [`src/irys/matter/reasoning.py:225`](../src/irys/matter/reasoning.py#L225). That leaves a real TOCTOU window: if the run completes after the API check but before the update, the API can still report success while the action lands on a completed run. I verified the primitive behavior directly: completed runs still accept `stop_requested=1` and `redirect_requested=1`. There is also still a wrong-run ambiguity on the matter-scoped stop endpoint: it stops the most recently started running non-utility run, not a caller-selected run [`src/irys/service/api.py:1367`](../src/irys/service/api.py#L1367). I reproduced that too with two concurrent real runs; `/matter/{matter_id}/stop` always targeted the newer one.

3. High: SO-1 durability still fails under the exact failure mode that matters most: deferred propagation persistence is best-effort. Both enqueue paths add work to memory, then swallow DB write failure and explicitly admit the queued items will not survive restart [`src/irys/matter/matter.py:343`](../src/irys/matter/matter.py#L343), [`src/irys/matter/matter.py:352`](../src/irys/matter/matter.py#L352), [`src/irys/matter/matter.py:418`](../src/irys/matter/matter.py#L418), [`src/irys/matter/matter.py:427`](../src/irys/matter/matter.py#L427). The new background flush loop improves eventual convergence after truncation [`src/irys/service/api.py:1974`](../src/irys/service/api.py#L1974), [`src/irys/service/api.py:2015`](../src/irys/service/api.py#L2015), but it does nothing for the admitted "DB write failed, restart loses the queue" case. That means durable matter-model state can still be lost under partial failure exactly where the code says it is supposed to be durable.

4. Medium: The r44 matter-isolation claim is still weaker than advertised on the SSE path. `stream_run_events()` validates matter ownership inside the generator and returns an error event over a `200 OK` stream instead of failing the HTTP request with `404` [`src/irys/service/api.py:2474`](../src/irys/service/api.py#L2474), [`src/irys/service/api.py:2490`](../src/irys/service/api.py#L2490). I reproduced this locally: a foreign-matter run ID returned `200` with `data: {"error": "run_id ... not found in this matter"}`. That is better than leaking events, but it is not the clean endpoint-level access enforcement the commit message claims.

5. Medium: Redirect is still phase-bound, not truly mid-run reliable. The engine only consumes redirect requests inside `_investigate_loop()` [`src/irys/rlm/engine.py:1658`](../src/irys/rlm/engine.py#L1658). If the run has already moved into verification or synthesis, the redirect can be accepted at the API layer and then never applied before the run exits [`src/irys/rlm/engine.py:1061`](../src/irys/rlm/engine.py#L1061), [`src/irys/rlm/engine.py:2794`](../src/irys/rlm/engine.py#L2794). The in-process backend at least warns that redirect takes effect at the next iteration boundary [`src/irys/ui/backends/in_process.py:333`](../src/irys/ui/backends/in_process.py#L333), but the service API does not.

6. Medium: SO-7 is still real, but its surfacing remains conditional on the run reaching late phases. Gap mining for quant conflicts, proof gaps, contradiction mining, version-chain gaps, and clarification generation all happen after the stop short-circuit [`src/irys/rlm/engine.py:1051`](../src/irys/rlm/engine.py#L1051), [`src/irys/rlm/engine.py:1064`](../src/irys/rlm/engine.py#L1064), [`src/irys/rlm/engine.py:1103`](../src/irys/rlm/engine.py#L1103). A user-interrupted run preserves partial state, but it can still skip the system's most proactive missingness surfacing work. That is not a recent regression, but it means SO-7 is strongest on completed runs, not on every run.

7. Low: The new test coverage is useful but incomplete relative to the r44/r45 claims. The added service tests cover assertion history, cross-matter run events, and cross-matter run stop [`tests/service/test_matter_api.py:533`](../tests/service/test_matter_api.py#L533), [`tests/service/test_matter_api.py:615`](../tests/service/test_matter_api.py#L615), [`tests/service/test_matter_api.py:630`](../tests/service/test_matter_api.py#L630). I do not see equivalent cross-matter tests for run redirect or the SSE stream path, which are exactly where the remaining semantic weakness sits.

8. Low: Utility-run isolation got better, but utility-run audit semantics are still noisy. `start_run()` seeds every run, including `manual_flush` and `background_flush`, with `why="User initiated investigation"` [`src/irys/matter/reasoning.py:66`](../src/irys/matter/reasoning.py#L66). So the system now avoids steering the wrong utility run, but it still records utility runs as if they were normal investigations in the ledger.

**Bottom Line**
The post-adv#030 fixes are real, but they do not justify upgrading SO-1, SO-2, or SO-3 to PASS. The strongest remaining problems are not the ones the new tests cover. They are the ones the code still explicitly permits: best-effort durability under DB failure, incomplete revision recording for canonical assertion mutations, and steering primitives that can succeed against the wrong or already-finished run. SO-7 did not drift; it remains one of the stronger outcomes in the current system.
