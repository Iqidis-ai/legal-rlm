- Cross-matter write throughput is still serialized at the repository DB. The moved user-lock read inside `BEGIN IMMEDIATE` adds only one indexed query to each recovery write, so it is not the main bottleneck; the real limit is that all writers for matters in the same repository share one SQLite file and one writer slot. Expected wait times are near-zero at low utilization, then cluster at roughly multiples of one node-write transaction under moderate contention, then develop a long tail under saturation. No explicit busy timeout/backoff is configured here, so once the queue is too deep you rely on sqlite defaults rather than a repo-level retry policy. Architectural implication: parallel BFS across matters in one repo will not scale linearly; if high write concurrency matters, shard by matter or move to a DB with row-level writer concurrency. - The JTMS analogy is only locally sound. The policy “active superseder defeats original; if all superseders become inert, recompute original from its speech-act baseline plus current support/attack graph” is reasonable for total replacement. **LOW**
- The supersession recovery path does add a narrow per-node N+1, but not a broad hot-path one. Normal neighbor state loading is still batched. The extra work appears only for recovering `SUPERSEDED` nodes: one occurrence scan to choose a baseline speech act, plus one in-transaction user-lock probe. So a single withdrawal does not touch all `1000` superseded assertions in the matter; it touches only the reachable subgraph from the withdrawn superseder. If one superseder directly fans out to `1000` targets, expect about `1000` extra occurrence reads and `1000` lock-row reads on top of the ordinary BFS node visits. Architectural implication: acceptable for rare recoveries, but bulk rollback should eventually use cached baselines or set-based recompute.
